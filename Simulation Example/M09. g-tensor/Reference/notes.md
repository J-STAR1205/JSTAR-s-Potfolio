# M09. g-tensor — 판단 노트

- `g_tensor.py`(Atoms 4, FD-SOI g-tensor): 6차 시도에서 성공. 원자 76,917개(원래 튜토리얼 269,934개에서
  축소, 이유는 메모리 — 아래 참고), 10개 고유쌍 계산에 1327초(22분), 전체 1716초(29분).
  `holes_soc_B.py`(Device 10)는 이전에 이미 성공적으로 실행 완료.
- 결과: g-tensor 대각 성분 ≈ 1.998~2.004 (자유전자 g=2에 근접), 비대각 SOC 비등방성 ≈ 4e-3 수준,
  평균 면내 spin-splitting ≈ 27,967 MHz/T — Si FD-SOI에서 기대되는 물리(약한 SOC 보정)와 일치.
- 계산 안정성: 원자 수를 줄이지 않은 원래 크기(269,934개)는 attempt당 약 70분이 걸리고 반복 재시도가
  필요했음. 축소한 76,917개 크기에서도 tight-binding 고유값 솔버가 가끔 매우 오래 걸리거나(한 attempt가
  5시간 넘게 안 끝난 사례 2회) 메모리를 11GB 이상 써서 시스템이 위험해지는 경우가 있었음 — 최종적으로는
  `memory_mode="robust"`(기본값) + `memory_threshold=None`(시스템 RAM 75%를 넘으면 디스크로 자동 offload)
  설정으로 안전하게 완료됨. 원자 박스나 요청 state 수(10개, g-tensor엔 0/1만 실제 사용)는 원본 튜토리얼
  설정을 그대로 유지함 — "제대로 계산·기능하는지" 판단이 목적이므로 결과를 쉽게 만들기 위한 임의 축소는
  하지 않음.

**판단**: 물리적으로 타당한 g-tensor가 나오지만, 계산이 가끔 (이번 세션에서 6번 중 1번) 수십 분~수 시간
수준으로 불안정하게 오래 걸리고 메모리를 많이 쓸 수 있음. Si/SiGe 전자에서 g 변화가 큐비트 주파수 오차에
의미 있는 크기인지는 (대각 성분이 2에 매우 가까워) 이 소자 조건에서는 크지 않아 보이나, 계산 자체의
실행 안정성(재현성 있는 실행 시간) 확보가 선행 과제로 보임 — 대규모/반복 스윕에 쓰기 전에 왜 특정
random tight-binding perturbation에서 유독 느려지는지 원인 파악이 필요.
